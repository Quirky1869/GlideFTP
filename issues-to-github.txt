#28
Title: [Bug] Multi-file transfer broken — drag-and-drop sends only 1 file; transfer button fails all
Labels: bug, critical
Version fixed: v1.2
Description:
With multiple files selected:
- Drag-and-drop only transfers the first file; the rest are silently ignored.
- The "Transfer" button queues all files but all fail. Retrying individually works.

Solution (closing comment):
Fixed in v1.2.
Two separate root causes:
1. Drag-and-drop (FileBrowser.svelte): the dragstart handler now checks if the
   dragged row is part of the current selection; if so it packs ALL selected
   entries into the drag data JSON array. The drop handler iterates the full
   array and queues a transfer per entry.
2. Concurrent FTP transfers (internal/connection/ftp.go): FTPClient gained a
   sync.Mutex protecting every method. The jlaffaye/ftp library is not
   thread-safe; without the mutex, concurrent queue workers corrupt the control
   connection, causing all parallel jobs to fail. With the mutex, each job
   acquires the lock for its operation in sequence.

#30
Title: [Bug] Cancel button in transfer queue has no effect
Labels: bug
Version fixed: v1.2
Description:
Clicking "Cancel" on a pending or in-progress transfer in the queue does nothing.
Ref: _images/issues/issue-7.png

Solution (closing comment):
Fixed in v1.2 in internal/transfer/queue.go.
Each Job now holds a `cancelFn context.CancelFunc` that is set when queue.run()
starts the job's goroutine. progressReader.Read() and progressWriter.Write() both
call `ctx.Err()` before processing each chunk and return an error if the context

method handles both cases: pending jobs are removed from the queue directly;
running jobs have their cancelFn() called.

Labels: enhancement

Description:

Solution (closing comment):
Implemented in v1.4.

  `wails.OnShutdown(ctx, func() { app.shutdown(ctx) })`

Root cause: FileSize() was called AFTER Retr() had already opened the data
connection. On Synology NAS (and some other FTP servers) issuing a SIZE command
on the control connection while a data transfer is in flight violates the FTP
state machine; the server replies with 0, causing the progress tracking to
believe nothing was transferred and the download was empty.
Fix: moved the FileSize() call to before Retr() so the size is known before the
data connection opens. The transfer then proceeds and completes normally.

Title: [Feature] Duplicate file detection with conflict resolution popup when transferring
Labels: feature, ui
Version fixed: v1.7.1
Description:

the app overwrites it silently. There is no way to know a conflict occurred or
choose what to do.

The expected behaviour is a popup dialog with four choices:
  - Replace — overwrite the existing file
  - Rename on host — save the transferred file with an auto-generated name
    locally (e.g. "file (1).txt")

#64
Title: [Security] Passwords stored in plain text in sites.json
Labels: enhancement, security
Version fixed: v1.7.3
Description:
Saved site passwords are written in plain text in the config file
~/.config/GlideFTP/sites.json. Anyone with access to the file (backup, sync,
export) can read all credentials without any protection.

Solution (closing comment):
Implemented in v1.7.3. Passwords are now stored in the OS system keyring and

Backend - new packages:

  [32B random salt][12B random nonce][ciphertext + GCM tag].

Backend - app.go changes:
- `sites.go save()` always strips passwords before writing to disk.
- `migratePasswords()` runs at startup: any plaintext password still present in
  an old sites.json is migrated to the keyring, then the file is re-saved stripped.

  returning to the frontend (so the form still shows the saved password).
- `CreateSite` / `UpdateSite`: password is extracted, cleared from the struct,
  then stored in the keyring. Auth types anonymous / ask_password / interactive
  never store a password (handled by `needsKeyring()`).
- `DeleteSite`: also calls `keyringMgr.Delete()`.
- `buildSiteConfig`: fetches the password from the keyring for each connection.
- New bindings: `GetKeyringStatus()`, `ExportSitesPlain()`,
  `ExportSitesEncrypted(passphrase)`, `OpenImportDialog()`, `DoImportSites(path, passphrase)`.

Frontend - SiteManager.svelte:
- Yellow warning banner shown when `GetKeyringStatus()` returns
  `"keyring_unavailable"`, with a message asking the user to install
  gnome-keyring or use "Ask password" auth.
- Export button now opens a two-step dialog:
  - Step 1: choice between "Without passwords" (plain .json) and

  - Step 2 (encrypted only): passphrase input + confirmation field, both
    with eye-toggle. Mismatched or empty passphrase is blocked client-side.
- Import: `OpenImportDialog()` opens the file picker and returns
  `{ path, needsPassphrase }`. If the file is a .gfe, a passphrase prompt
  is shown before calling `DoImportSites(path, passphrase)`. Plain JSON
  imports (including old-format files with plaintext passwords) are handled
  transparently - passwords found in the JSON are stored in the keyring on
  import.

Cross-platform export/import:
The .gfe format uses only Go stdlib crypto primitives - it is fully portable
between Linux and Windows. A file exported on Linux can be imported on Windows
and vice versa.

Linux - keyring availability (Arch):
Arch users on minimal setups may not have gnome-keyring or kwallet installed.
A README.md is included in the Arch AppImage archive with check and install
commands. If no keyring daemon is running, the banner guides the user to use
"Ask password" auth instead.

Title: [Bug] "Clear" button in the Failed tab of the transfer queue has no effect
Labels: bug
Version fixed: v1.7.4
Description:
Clicking the "Clear" (Vider) button in the "Failed" tab of the transfer queue

  if (activeTab === 'failed') {

Each call triggers a separate `ClearTransfers` binding → `queue.Clear()` on the

event handler filters out all matching jobs from the store.

#69
Title: [Bug] Concurrent transfer option has no effect — transfers happen one by one
Labels: bug
Version fixed: v1.7.4
Description:
The "Max simultaneous transfers" setting in Settings > Transfers has no visible
effect. Even when set to 3 (or more), files are transferred one at a time
regardless of the value chosen.

Two independent root causes:

1. SaveSettings() did not update the queue's semaphore.
   The transfer queue (Queue) is created at startup with a buffered semaphore
   channel sized to MaxConcurrentTransfers. When the user saves new settings,
   SaveSettings() in app.go updated the speed limit via queue.SetSpeedLimit() but
   never updated the semaphore capacity. Any change made to MaxConcurrentTransfers
   after startup was therefore silently ignored — the queue kept using the
   semaphore from startup for the lifetime of the app.

2. FTP serializes all transfers through a single global mutex.
   FTPClient.Upload() and FTPClient.Download() both acquired c.mu (a sync.Mutex)
   at the very start of the function and held it until the transfer completed.
   Because jlaffaye/ftp is not thread-safe on a single connection, the mutex was
   there to prevent data corruption — but holding it for the full duration of
   every transfer meant only one goroutine could transfer at a time, making the
   semaphore in the queue irrelevant for FTP sessions. SFTP was not affected
   (github.com/pkg/sftp natively supports concurrent requests over a single SSH
   connection via packet IDs).

Solution (closing comment):
Fixed in v1.7.4 — two separate fixes.

**Fix 1 — queue.go: SetWorkers() + run() semaphore snapshot**

A new method SetWorkers(n int) was added to Queue:

  func (q *Queue) SetWorkers(n int) {
      q.mu.Lock()
      q.workers = n
      q.sem = make(chan struct{}, n)
      q.mu.Unlock()
  }

run() was updated to snapshot q.sem into a local variable before the select,
so that both the acquire and the deferred release always use the same channel
even if SetWorkers() replaces q.sem mid-flight:

  q.mu.Lock()
  sem := q.sem
  q.mu.Unlock()
  select {
  case sem <- struct{}{}:
  ...
  }
  defer func() { <-sem }()

Without this snapshot a goroutine that acquired from the old semaphore would
have released from the new one (pointing at an empty channel) → deadlock.

**Fix 2 — app.go: propagate the setting change to the queue**

SaveSettings() now calls SetWorkers in addition to SetSpeedLimit:

  func (a *App) SaveSettings(s settings.Settings) error {
      a.appSettings = &s
      a.queue.SetWorkers(s.MaxConcurrentTransfers)
      a.queue.SetSpeedLimit(s.MaxTransferSpeedKBps)
      return s.Save()
  }

**Fix 3 — ftp.go: dedicated connection per FTP transfer**

The global mutex on Upload() and Download() was removed. Each call to Upload()
or Download() now opens its own dedicated FTP connection via a new internal
dial() helper (same credentials as the primary connection):

  func (c *FTPClient) Upload(ctx context.Context, ...) error {
      conn, err := c.dial()
      if err != nil { return err }
      defer conn.Quit()
      // ... transfer using conn, no shared lock
  }

This is the standard approach used by all major FTP clients (FileZilla, etc.):
since FTP only allows one active data transfer per control connection, N
concurrent transfers require N separate control connections. The primary
connection (c.conn) is preserved exclusively for control operations (ListDir,
MkDir, Delete, Rename, CurrentDir) which continue to be serialized by c.mu as
before.

Title: [Bug] Transferring a folder fails with "550 Not a regular file"
Labels: bug
Version fixed: v1.7.4
Description:
Attempting to transfer a folder (either upload or download) results in the
transfer immediately failing with the error:

  550 /path/to/Folder: Not a regular file

The error appears on every retry attempt, keeping the entry permanently in the
"Failed" tab.

Root cause:
QueueUpload() and QueueDownload() passed the path directly to executor.Upload()
/ executor.Download(), which call conn.Stor() / conn.Retr() (FTP) or
client.Create() / client.Open() (SFTP) on the given path. Both FTP and SFTP
protocols only allow RETR/STOR on regular files; issuing them on a directory
path causes the server to return 550. There was no check for whether the
queued path was a file or a directory — folders were silently treated as files
and the transfer always failed.

Solution (closing comment):
Fixed in v1.7.4.

Two new Go methods were added to app.go for recursive directory transfers:

**QueueUploadDir(localPath, remotePath string)**
Runs asynchronously (goroutine). Calls enqueueUploadDir() which:
1. Creates the remote directory via connMgr.MkDir(remotePath).
2. Lists the local directory with os.ReadDir(localPath).
3. For each file entry: queue.Add(Upload, src, dst, host).
4. For each subdirectory: recurse into enqueueUploadDir(src, dst).

**QueueDownloadDir(remotePath, localPath string)**
Runs asynchronously (goroutine). Calls enqueueDownloadDir() which:
1. Creates the local directory with os.MkdirAll(localPath, 0755).
2. Lists the remote directory via connMgr.ListDir(remotePath).
3. For each file entry: queue.Add(Download, dst, e.Path, host).
4. For each subdirectory: recurse into enqueueDownloadDir(e.Path, dst).

The result is one transfer queue job per file in the folder tree, each
independently visible, cancellable, and retryable in the queue panel.

Both methods were exported to the frontend via new entries in
frontend/wailsjs/go/main/App.js.

**FileBrowser.svelte — doQueueTransfer():**
The function now checks entry.isDir before deciding which binding to call:

  if (entry.isDir) {
    if (side === 'local') QueueUploadDir(entry.path, dest);
    else QueueDownloadDir(entry.path, dest);
  } else {
    if (side === 'local') QueueUpload(entry.path, dest);
    else QueueDownload(entry.path, dest);
  }

**FileBrowser.svelte — drag-and-drop:**
handleDragStart() now includes isDir in the serialized drag payload:
  entries: dragEntries.map(en => ({ path, name, isDir: en.isDir }))
handleDrop() reads isDir from each entry and routes to QueueUploadDir /
QueueDownloadDir / QueueUpload / QueueDownload accordingly.

Title: [Bug] Connection drops silently after a few minutes; timeout setting has no effect on idle

Description:

1. The connection drops silently after 5-10 minutes of inactivity regardless

The "Connection timeout (seconds)" setting controls the TCP dial timeout and

The actual cause of the drops is the FTP/SFTP server's own idle timeout

inactivity on the control connection. GlideFTP was sending nothing to keep the
connection alive, so the server would silently drop it.

Moving the mouse does NOT reset the server's idle timer — only network activity
on the control connection does. Without keepalives, the connection will always
drop regardless of what the user does on the client side.

The default connection timeout was also set too low (30 seconds) for an
operation timeout, making slow servers appear to time out during normal use.

**1. Default timeout raised to 15 minutes (internal/settings/settings.go)**

- The TCP dial timeout when establishing a new connection.
- The ListDir operation watchdog (the guard that disconnects if a directory
  listing hangs for longer than the configured value).

**2. Keepalive goroutine — prevents server-side idle drops (internal/connection/)**

A Keepalive() method was added to the Client interface and implemented by both
clients:

FTPClient.Keepalive() (ftp.go):
  Sends a NOOP command on the primary control connection.
  Uses sync.Mutex.TryLock() so it never blocks if another control operation
  (ListDir, MkDir, etc.) already holds the lock — in that case the server is
  clearly active and the keepalive tick is safely skipped.

SFTPClient.Keepalive() (sftp.go):
  Sends an SSH global request "keepalive@openssh.com" on the underlying SSH
  connection. OpenSSH responds with a failure reply (not an error) if it does
  not recognise the request type; what matters is that the TCP roundtrip
  succeeds. If the TCP socket is dead the call returns an error immediately.

Manager.startKeepalive() (manager.go):
  Called automatically after every successful connection (doConnect()).
  Runs a goroutine with a 60-second ticker:
  - Each tick checks whether the connection ID is still present in the
    manager's active list; if not (normal user disconnect), the goroutine
    exits cleanly without calling onLost.
  - If the ID is still present, calls client.Keepalive().
  - On keepalive error: removes the entry from the manager, updates activeID
    if needed, and calls onLost(id, host) only if the entry was actually
    found and removed (guards against a race with a concurrent normal
    disconnect).

**3. User notification on unexpected disconnect (app.go + App.svelte)**

app.go startup():
  Registers a SetOnConnectionLost callback on the manager that emits a Wails
  event "connection:lost" with { id, host } when a keepalive detects a dead
  connection.

App.svelte onMount():
  Subscribes to "connection:lost" via EventsOn:
  - Calls closeTab(id) to remove the dead tab and update all connection
    stores (identical to a normal user-initiated tab close).
  - Sets lostNotif = { host }, showing a dismissible red banner:
    "⚠ Connection lost — The connection to <host> was dropped by the server.
    Please reconnect."
  - The banner auto-dismisses after 10 seconds; the ✕ button dismisses it
    immediately.

i18n: connectionLost / connectionLostDetail keys added to en.js and fr.js.

Title: [Feature] Intra-panel drag-and-drop, copy and cut/paste for local and remote panels
Labels: enhancement
Version fixed: v1.7.4
Description:
No way to copy, move, or reorganise files within the same panel. Requested
behaviours:

- Drag a file or folder onto a subfolder or the ".." row within the same panel
  to move it there.
- Ctrl+C / Ctrl+X / Ctrl+V (and right-click Copy / Cut / Paste) to copy or
  move files and folders within the local panel or within the remote panel.
- Works in both list view and tree view.
- Local → Local: real recursive copy (no network involved).
- Remote → Remote: transparent copy via temp-file download + re-upload (no
  native FTP/SFTP server-side copy command exists).
- Cross-panel operations are transfers, not copies — not in scope here.
- Auto-refresh while the operation is running (first at +1 s, then every 4 s),
  plus a final refresh when done.
- Green confirmation banner on success, orange on failure, auto-dismissed
  after 4 seconds.

Solution (closing comment):
Implemented in v1.7.4.

**Go backend:**

internal/fs/local.go — Copy(src, dst string) error:
  Recursive local copy. Detects file vs directory via os.Stat. For files:
  os.Open → os.Create → io.Copy. For directories: os.MkdirAll + recurse into
  each entry. Used by the new app.LocalCopy binding.

internal/connection/manager.go — CopyRemote / CopyRemoteDir:
  CopyRemote(srcPath, destPath): downloads the remote file to a OS temp file
  (os.CreateTemp), re-uploads it to the destination, then deletes the temp
  file. Works for both FTP and SFTP without requiring any server-side COPY
  command. Runs synchronously so the JS caller can await completion.
  CopyRemoteDir(srcPath, destPath): synchronous recursive variant — MkDir at
  destination, ListDir at source, recurse into subdirectories, CopyRemote each
  file. Synchronous so that onRefresh() in the frontend fires only after the
  full tree is copied.

app.go: LocalCopy, RemoteCopy, RemoteCopyDir — thin wrappers over the above.

frontend/wailsjs/go/main/App.js: LocalCopy, RemoteCopy, RemoteCopyDir
  bindings added.

**Frontend — clipboard store (connection.js):**
  export const clipboard = writable(null);
  Shape: { entries: [{path, name, isDir}], operation: 'copy'|'cut',
           side: 'local'|'remote' }
  Shared between both FileBrowser instances so a clipboard set in one panel is
  visible to the other (though paste is rejected when side !== currentSide).
  Cleared automatically after a successful cut+paste.

  New helpers: localCopy(src, dest), remoteCopy(src, dest),
  remoteCopyDir(src, dest).

**Frontend — FileBrowser.svelte:**

Keyboard (handlePanelKeydown):
  Ctrl+C → copyEntries(selected) — sets clipboard with operation 'copy'.
  Ctrl+X → cutEntries(selected) — sets clipboard with operation 'cut'.
  Ctrl+V → pasteToFolder(path) if clipboard.side === side.

Right-click context menu:
  Cut and Copy buttons always visible on file/folder items.
  Paste button visible only when $clipboard.side === side.
  Paste routes to pasteToFolder(contextEntry.isDir ? contextEntry.path : path)
  so right-clicking a subfolder pastes directly into it.

pasteToFolder(destFolder):
  Iterates clipboard.entries. For each entry:
    cut  → onRename(src, dest)       (local or remote move via rename)
    copy + local → localCopy(src, dest)
    copy + remote file → remoteCopy(src, dest)
    copy + remote dir  → await remoteCopyDir(src, dest)
  Progressive refresh: setTimeout 1 s → onRefresh(), then setInterval 4 s →

  handleDropOnFolder(e, destFolder): reads drag data; if fromSide === side →

  ".." row gets drag handlers with parentPath as destination.
  Tree dir nodes get draggable + dragstart (packs node into drag payload) +

#73
Title: [Feature] Deleted local files go to system trash / recycle bin instead of being permanently deleted
Labels: enhancement
Version fixed: v1.7.4
Description:
When deleting a file or folder from the local panel (Delete key, right-click
→ Delete, or multi-selection delete), the item disappears permanently. It does
not appear in the OS trash / recycle bin, making recovery impossible without
a third-party tool.

Expected behaviour: deleting from the local panel should move the item to the
system trash (Linux) or Recycle Bin (Windows), just like deleting from a
standard file manager.

Note: this feature only applies to the local panel. Remote files (FTP/SFTP)
are deleted on the server and there is no server-side trash mechanism in
either protocol.

Solution (closing comment):
Fixed in v1.7.4.

Three platform-specific files were added to internal/fs/ using Go build tags.
app.go LocalDelete() now calls localfs.Trash() instead of localfs.Delete().

**Linux — internal/fs/trash_linux.go (//go:build linux)**

Implements the FreeDesktop.org XDG Trash specification:

1. Determines the trash directory:
   $XDG_DATA_HOME/Trash, falling back to ~/.local/share/Trash.
2. Creates files/ and info/ subdirectories with mode 0700 if absent.
3. Resolves a unique name for the trashed item (collision avoidance:
   appends .1, .2, ... before the extension until a free slot is found).
4. Moves the item via os.Rename (fast, atomic, no data copy).
   Cross-device case (EXDEV): falls back to localfs.Copy() + os.RemoveAll()
   so files on separate filesystems (e.g. a second partition) are still
   handled correctly.
5. Writes the .trashinfo sidecar file:
   [Trash Info]
   Path=/absolute/original/path
   DeletionDate=2024-06-01T14:30:00

The trashinfo format is compatible with Nautilus, Thunar, Dolphin, Nemo,
and any other FreeDesktop-compliant file manager.

**Windows — internal/fs/trash_windows.go (//go:build windows)**

Calls SHFileOperationW from shell32.dll via syscall.NewLazyDLL (no CGo
required, compatible with mingw-w64 cross-compilation from Linux).

The SHFILEOPSTRUCTW struct is reproduced in Go with explicit padding fields
to match MSVC's 64-bit layout (56 bytes total):
  hwnd, wFunc, _pad1, pFrom, pTo, fFlags, _pad2, fAborted, hMapping, title.

Flags used:
  FOF_ALLOWUNDO      (0x0040) — sends to Recycle Bin, recoverable
  FOF_NOCONFIRMATION (0x0010) — no Windows dialog
  FOF_SILENT         (0x0004) — no progress window
  FOF_NOERRORUI     (0x0400) — suppress error dialogs (errors returned as int)

The pFrom path is encoded as a double-null-terminated UTF-16 multi-string
(required by SHFileOperationW): unicode/utf16.Encode([]rune(path + "\x00\x00")).

**Fallback — internal/fs/trash_other.go (//go:build !linux && !windows)**

Falls back to permanent deletion (os.RemoveAll) on unsupported platforms so
the package still compiles everywhere.
